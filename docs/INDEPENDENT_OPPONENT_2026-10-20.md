A09 **CONFIRMED прямым SQL**: валидно связанный второй pending offer можно вставить при уже занятом резервом последнем месте; GET capacity после этого показывает `available=-1`. Также SQL позволяет переписать `vacancy_versions.reason` и `created_by`, не входящие в immutable trigger. Это **не доказанный обход через доступный приложению API и не самостоятельная уязвимость пользователя**. В самом SQL написано, что cross-record triggers не заменяют сервисную сериализацию. Корректный вывод: гарантии БД уже гарантий сервиса; администратор/новый writer должен соблюдать протокол. Требовать универсальных триггеров вместо сервисных проверок без причины было бы предпочтением ревьюера. Но заявление «БД сама гарантирует capacity/полную неизменяемость истории» опровергнуто.

В capacity-операциях сначала читается startup_id целевого объекта, затем блокируется startup, затем актуальные статус/лимит/offer/попытка перечитываются. `act_on_app` также перечитывает attempt после ожидания. Create version и submit используют тот же gate. В проверенных маршрутах grant проверяется после получения startup lock. Ошибки через dependency `engine.begin()` откатывают всю команду; положительный пример — нет половинчатого membership; отрицательный — R06 с expiry. Публичный GET capacity меняет состояние expired offers без CSRF, но в этой пробе не совершает неразрешённый найм: это не названо отдельной CSRF-уязвимостью.

### Управляемая конкурентность: 10 пар, по два порядка

В `test_controlled_concurrency` отдельное соединение держит `startups ... FOR UPDATE`. Первый запрос запускается отдельным worker, подтверждается ожидание lock через `pg_stat_activity`, затем запускается второй и подтверждаются два ожидающих независимых backend transactions. Gate освобождается. Это не просто последовательные запросы с условной «конкурентностью». Проверены итоги offer/attempt/active membership/capacity; отдельно — версия новой попытки и статус submission. Полный дамп всех колонок всех таблиц не делался.

5. Ответ reset потерялся; кандидат успел подать заново; клиент повторил тот же запрос с тем же ключом. Почему новая работа снова reset и появилась ещё одна версия? **R05.**
6. Почему после отказа принять просроченное приглашение оно всё ещё pending в БД, а вызов capacity посторонним пользователем меняет его на expired? Как вы определяете актуальное состояние? **R06.**
7. Зачем постороннему нужны даты вступления и ухода бывших участников, если собственная спецификация запрещает раскрывать private history? **R07.**
8. Как кандидат сдаст новую critical-версию теста, если старое решение уже superseded, а offer_pending запрещает submit? Что означает `test.reviewed` при нуле обновлённых строк? **R11/R14.**
9. Как применятся новые триггеры к БД, уже помеченной `0001_initial`, если новой ревизии нет? Чем fresh migration доказывает upgrade? **R13.**
10. Почему при 104 публикациях последняя часть недостижима, архивный собственный проект исчезает из кабинета, а пользователь не видит названия проекта у своего отклика? Какие из 12 групп вы действительно готовы показать без ручного API? **R09/R10/R12.**

## Пять коротких демонстраций слабостей

1. **Два аккаунта и кабинет.** Создать vacancy, реальный application и offer; войти кандидатом → «Мой кабинет». Показать SQL/HTTP-подтверждение существующих объектов рядом с нулевыми счётчиками UI. Сильнейший blocker, без edge cases. **R01.**
2. **Стартап без вакансий.** Создать активный проект с разрешёнными общими откликами; другой аккаунт делает один штатный general apply →500. В IAB использовать HTTP из-за неподдерживаемого prompt, не подменять этим backend-дефектом UI-ограничение. **R02.**
3. **Смена роли.** Кандидат получает offer, затем recruiter grant; отзывает свой offer как manager →200 и reviewing. Сравнить с кандидатским decline →declined на отдельном примере. **R03.**
4. **Потерянный ответ.** Reset с key K → resubmit кандидата → replay исходного reset K. Показать две новые версии и сброшенную свежую попытку. **R05.**
5. **История на защите.** Две попытки с разными письмами и версиями, offer с особым сообщением, revoke, reject с причиной. Попросить кандидата восстановить первую попытку, условия offer и причину через продукт. Сопоставить с БД, где часть данных есть, а причина не была записана. **R04.**

## Минимальный порядок устранения перед сдачей

1. **Вернуть основной путь:** R01 и R02, затем реальный двухпользовательский UI-сценарий с положительным и отрицательным решением; базовая регрессия на list и general apply.
2. **Закрыть нарушенные права и штатные ошибки:** R03, R07, R08. Матрица ролей должна проверять комбинации, не только отдельные роли.
3. **Стабилизировать команды и состояния:** replay массового reset/create, expiry без отката наблюдаемого исхода, critical/offer_pending, честные review events. Повторить затронутые конкурентные сценарии после изменения порядка locks/транзакций.
4. **Сделать историю и кабинет полезными:** исходные письма, версии/условия конкретного offer, причина решения, собственные и управляемые проекты независимо от public feed, содержательные имена, реальные страницы.
5. **Подготовить путь обновления:** получить настоящую предыдущую схему, incremental migration и тест с данными; свежий install оставить отдельной проверкой.
6. **Завершить заявленный scope через UI либо явно согласовать уменьшение:** сначала востребованные состояния/команда/рекрутеры, затем версии/тестовые/история. Не тратить это время на рекомендации, микросервисы и необязательную Telegram-интеграцию.
7. **Повторная сдачная проверка:** чистая сборка, полноценный UI в поддерживаемом браузере, desktop/mobile, сохранение с постоянным volume на отдельном безопасном стенде, актуальный README. Кандидат лично заполняет свой AI-пример и реальные затраты времени; проверяется предъявленная ссылка репозитория. Публикация/push в аудите не выполнялись.
