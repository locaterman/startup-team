# Telegram-вход: реализация и следующий шаг

21 октября 2026. Код v0.5.0. Пользователь предоставил username бота: [@test_q_buisness_club_bot](https://t.me/test_q_buisness_club_bot). Реальный токен не передавался; подключение backend, адрес HTTPS и настройка Mini App ещё не выполнены.

## Что реализовано

- POST `/api/v1/auth/telegram` принимает только raw `init_data`, проверяет HMAC по токену бота, auth_date, обязательного пользователя, тип/диапазон ID, дубли и некорректное кодирование.
- Новый подтверждённый Telegram ID создаёт пользователя; повторный вход находит того же пользователя. Telegram-only аккаунт не требует фиктивного email/пароля. По имени, username или email аккаунты автоматически не объединяются. Редактированный профиль не перезаписывается именем Telegram при следующем входе.
- Применяется существующая HttpOnly / SameSite=Lax сессия, CSRF и права доступа. В HTTPS-конфигурации cookie Secure. Ротация входа отзывает прежнюю сессию этого браузера; другие устройства не разлогиниваются.
- Launch credential потребляется транзакционно. Повтор в том же браузере с его действующей сессией возвращает профиль без создания сессии; повтор без связанной сессии — 409. После logout нужно заново открыть Mini App через бота.
- По умолчанию новый обмен разрешён в течение 300 секунд после auth_date, допустимое опережение часов — 30 секунд. Старый launch может восстановить только уже связанную активную сессию того же браузера; он не создаёт новый вход. Срок сессии — 7 дней. Серверу нужна корректная синхронизация времени.
- Первый вход показывает заполнение профиля в новой визуальной системе. PATCH `/users/me` с валидным явным name завершает onboarding. GET `/auth/context` сообщает, нужен ли этот экран. До завершения сервер отклоняет доменные команды с `403 ONBOARDING_REQUIRED` через общую dependency `domain_auth`; чтение, редактирование своего профиля и logout доступны. Существующие demo-аккаунты не блокируются. Это серверное правило, а не только выбор React-экрана.
- GET `/auth/config` раскрывает только доступность Telegram/demo; токен, Telegram ID и служебные поля не попадают в публичные профили. Сохраняются HMAC-дайджесты обменов, не raw initData. Просроченные записи обменов очищаются при новом успешном входе.
- Демо-вход сохранён для локальной разработки. `ALLOW_DEMO_LOGIN=false` выключает password endpoint, `SEED_DEMO_ACCOUNTS=false` выключает создание демоаккаунтов, не удаляя существующие записи.

Миграция `0003_telegram_auth` отдельно расширяет users и создаёт таблицу потреблённых обменов. Старые пользователи, UUID, пароли, сессии, проекты и связи не пересоздаются. Downgrade forward-only: восстановление из проверенной резервной копии. На основной базе эта миграция в данном этапе не выполнялась.

Алгоритм и SDK сверены с [официальной документацией Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app). Вход использует только `initData`, не доверяет `initDataUnsafe`.

## Проверка, выполненная без реального бота

- Сборки backend и frontend успешны. OpenAPI: 67 операций, 49 схем, missing/extra 0.
- 67 стандартных/регрессионных проверок (42 прежних + 25 новых auth-проверок), затем 24 неизменённых независимых safety probes: **91 passed** на одноразовой PostgreSQL 16 без сети наружу и без основной базы.
- Новые проверки: подделка/другой токен, дубли полей, Unicode, malformed payload, неверные ID, expiry/future, две конкурентные регистрации одного ID, запрет объединения по имени, профиль/CSRF, replay в другом браузере, logout, сохранение профиля, выключенные способы входа.
- Upgrade-тесты обновлены для новой head revision; прежние случаи сохранения и отказа при повреждённых связях сохранены. Предел: это совместимые тестовые схемы и наблюдаемый schema-only snapshot, не все возможные данные рабочей базы.
- Браузер на отдельной tmpfs-базе: подставлен явно тестовый SDK с самостоятельно подписанными вымышленными launch-данными. Backend действительно проверил подпись, создал пользователя и сессию; через UI сохранены профиль/навыки, reload не повторил onboarding, новый аккаунт создал проект. Это **не проверка настоящего Telegram WebView**.
- Экран профиля на 320/390/768/1440 px без горизонтального переполнения. Ошибок JS в наблюдаемом прогоне нет. Артефакты: `docs/audit/telegram-2026-10-21/`. Предупреждение Starlette о будущем переходе TestClient с httpx на httpx2 не является падением теста.

Повторить backend-проверки:

```bash
docker build -f backend/Dockerfile -t startup-team-telegram-api:local .
python3 tools/verify_telegram.py
```

## Шаг 1: создать бота

В Telegram откройте [@BotFather](https://t.me/BotFather), отправьте `/newbot`, задайте отображаемое имя и свободный username, заканчивающийся на `bot`. Полученный токен сохраните в секретах сервера. В чат, Git и скриншоты токен не отправляйте.

До настройки сервера достаточно создать бота и сообщить его **username**. Токен используется только backend. Для развёртывания также понадобятся домен и существующий SSH-доступ либо панель хостинга.

## Шаг 2: подготовить сервер и HTTPS

Заготовлены `compose.production.yaml`, `deploy/Caddyfile`, `deploy/server.env.example`. Шаблон не запускался на удалённом сервере. Он требует заполненных переменных и не имеет рабочего значения домена по умолчанию.

Перед запуском проверить окружение хостинга: Docker/Compose, свободные 80/443, DNS домена на этот сервер, firewall и отсутствие конфликта с существующим reverse proxy. Если на сервере уже есть proxy, адаптировать подключение к нему, не останавливать его вслепую. Для новой установки шаблон поднимает собственный PostgreSQL-том; перенос данных с Mac — отдельная backup/restore операция, не автоматическая синхронизация.

Если переносить проекты, созданные под демоаккаунтами, они сохранят прежних владельцев. Привязка к реальным Telegram-аккаунтам требует отдельного явного сопоставления; она не выполняется автоматически по совпадению имени. Не выключать доступ владельцам существующих рабочих проектов без плана такого перехода.

На сервере скопировать `deploy/server.env.example` в игнорируемый `deploy/server.env`, заполнить домен, токен и два независимых случайных hex-секрета; ограничить права файла `chmod 600 deploy/server.env`. Переменные не выводить через `docker compose config` без `--quiet`.

После подготовки, из корня проекта на сервере:

```bash
docker compose --env-file deploy/server.env -p startup_team_production \
  -f compose.yaml -f compose.production.yaml up -d --build
```

Обновление существующей базы требует backup заранее. Имена Compose-проектов нельзя менять случайно: они определяют используемые тома. Обычный down сохраняет тома, `down -v` удаляет их.

## Шаг 3: подключить Mini App

После доступности HTTPS-адреса в BotFather `/mybots` → выбрать бота → настройки Mini App / Main Mini App и указать адрес приложения. Названия пунктов могут различаться между клиентами; используется реальный HTTPS URL развернутого приложения. Запускать из профиля бота или Mini App/menu button, передающего initData пользователя; ввод произвольного Telegram ID не поддерживается.

Проверить с двумя настоящими аккаунтами: первый вход/профиль, повторный вход без дубля, публикация, отклик, приглашение, согласие и членство; затем Telegram iOS/Android, клавиатуру, возврат и отступы. Telegram BackButton/content-safe-area и полная интеграция нового complete-дизайна — последующие задачи.

Вне Telegram остаётся браузерный режим, а не Telegram Login Widget. Отдельная email-регистрация и внешние Telegram-уведомления пока не добавлялись. На данном этапе удалённого deployment, реального токена, настройки BotFather, коммита и push не было.
