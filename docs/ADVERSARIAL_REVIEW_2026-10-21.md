## 2. Находки по приоритету

Обозначения: CONFIRMED/runtime — воспроизведено на временной PostgreSQL; CONFIRMED/source — доказано по исполняемой ветке кода, отдельный браузерный контрпример не выполнялся. ### F1. Критическое тестовое можно обойти отзывом и восстановлением заявки

**CONFIRMED/runtime, P2, доменный дефект.** Источник: S2 §5.9, INV-13/19; S3: критическая версия влияет на незавершённые процессы и сохраняет завершённые наймы.

Код: [main.py:799](../backend/app/main.py#L799), фильтр статусов на строке 803; восстановление [main.py:404](../backend/app/main.py#L404). Аналогичный узкий набор состояний есть в `complete/rules.ts`, `unfinished`/`criticalTest`.

Предусловия: активный проект, открытая вакансия с будущим intake, initial test v1, кандидатская заявка. Созданы решение v1 и отметка reviewed.

Шаги:

1. Кандидат отправляет `POST /applications/{a}/withdraw`.
2. Менеджер публикует `POST /vacancies/{v}/tests/versions` с `change_type=critical`, новым описанием и будущим test deadline.
3. Кандидат выполняет `POST /applications/{a}/restore`.
4. Читает `/applications/{a}/test-submissions`.

Ожидание: восстановленная незавершённая попытка учитывает критическую версию; старое решение сохраняется как историческое, но не выдаётся за актуально проверенное решение новых условий.

Факт: restore → 200/pending, старое решение v1 остаётся **reviewed**. Подача нового решения на v1 уже запрещена через TEST_VERSION_CONFLICT. Таким образом, два пути к одной активной попытке дают разную актуальность старого решения.

Последствие: рекрутер видит «проверено» у устаревшего решения и может ошибиться при оценке. Автоматического обязательного барьера тестового перед наймом нет по замыслу, поэтому это не обход обязательной проверки перед вступлением.

Первопричина: актуальность решения пересчитывается только в момент создания critical и только для pending/reviewing/offer_pending; restore не сверяет историю критических версий. withdrawn обратим, но оказался за пределами пересчёта.

Минимальное направление исправления: при restore под блокировкой проекта согласовать актуальность решений с последующей critical-версией. Можно хранить факт reviewed отдельно от текущей пригодности, либо выставлять superseded, сохраняя reviewer/time/event. Завершённые joined/rejected и прошлые попытки не переписывать.

Критерий достаточности: submitted/reviewed → withdraw → critical → restore дают историческое неактуальное решение; ordinary не инвалидирует; joined не меняется; гонка restore/critical даёт одинаковый итог в обоих порядках. Доказательство: `test_withdrawn_critical_old_submission_revives` в приложенном probe.

### F2. Прототип обещает повторную сдачу, которую API запрещает

**CONFIRMED/runtime + source, P2, препятствие прямому переносу дизайна.** Источник: S2 §§5.9–5.10, S3: переносить без потери функций и без подмены демонстрации серверной реализацией. Само право многократной сдачи одной версии не выведено как обязательное из S1/S2.

Код: [complete/main.tsx:1042](../design/prototypes/src/complete/main.tsx#L1042), [rules.ts:298](../design/prototypes/src/complete/rules.ts#L298), [invariants.ts:89](../design/prototypes/src/complete/invariants.ts#L89); сервер [main.py:838](../backend/app/main.py#L838); `0001_schema.sql` также имеет UNIQUE(attempt_id,test_version_id).

Шаги: в одной активной попытке дважды отправить HTTPS-ссылку для одного test_version_id. В макете кнопка называется «Отправить другое решение», запись добавляется в массив. Его invariant прямо требует две ссылки. Через API первый POST → 201, второй, с иной ссылкой → **409 TEST_ALREADY_SUBMITTED**.

Ожидание для интеграции: действие и текст интерфейса соответствуют серверному правилу. Факт: макет и тест закрепляют поведение, противоположное работающему API.

Последствие: механическое подключение кнопки к API ломает демонстрируемое действие. «27 зелёных invariants» здесь подтверждают внутреннюю согласованность другой модели, а не совместимость.

Первопричина: независимые localStorage-правила и DTO не сверены с ограничениями серверной попытки/версии.

Минимальное исправление без расширения backend: не предлагать повторную сдачу уже сданной версии; показывать существующее решение и разрешать другую допустимую версию. Если пользователь отдельно согласует ревизии решений одной версии — проектировать append-only revision на backend/БД/API, а не заменять старую ссылку. Это дополнительное решение, не обязательное условие исходного задания.

Достаточность: одна и та же таблица разрешённых действий используется в acceptance-проверке макета и API; повтор с тем же Idempotency-Key воспроизводит квитанцию, новая команда не обещает неподдерживаемую сдачу. Runtime: `test_repeated_solution_api`; макетные две сдачи заново выполнены Docker-build через invariants.ts.

### F3. Onboarding — экранный барьер, серверные команды до него доступны

**CONFIRMED/runtime, P2 как ограничение первого входа; не обход аутентификации.** Источник: S3 прямо требует проверить обход onboarding; S4 TELEGRAM_SETUP описывает первый вход/завершение профиля. S1 не доказывает обязательность серверного запрета всех команд до заполнения.

Код: [security.py:27](../backend/app/security.py#L27), [main.py:252](../backend/app/main.py#L252), [App.tsx:394](../frontend/src/App.tsx#L394). auth читает onboarding_completed_at, но проверяет лишь сессию/CSRF. Запрет находится в выборе React-экрана.

Шаги:

1. Войти с корректно подписанным вымышленным initData нового ID в изолированном тесте.
2. GET `/auth/context` → onboarding_required=true.
3. Получить собственный `/auth/csrf`.
4. Не вызывать PATCH профиля; отправить POST `/startups` с title.
5. Ещё раз прочитать context.

Факт: POST → **201**, onboarding_required всё ещё true. Ожидание, если onboarding объявляется обязательным перед работой: доменная команда отклоняется до завершения профиля. Если это добровольная UX-подсказка — поведение следует именно так документировать.

Последствие: нельзя защищать решение словами «сервер требует сначала заполнить профиль». При этом личность всё равно проверена HMAC, имя взято из подписанного Telegram-профиля, CSRF соблюдён; чужого доступа этот сценарий не даёт.

Первопричина: состояние процесса входа не является доменной политикой авторизации.

Минимальное исправление при обязательном onboarding: отдельная dependency для доменных команд; разрешить auth/context/csrf/logout и заполнение профиля. Не блокировать завершение onboarding самой dependency. Если ограничение не нужно — явно признать экран рекомендательным.

Достаточность: новый TG-пользователь до PATCH получает ожидаемый отказ на создание проекта/отклик/управление, после PATCH проходит; существующие demo-пользователи продолжают работать. Probe: `test_onboarding_bypass`.

### F4. Число мест вне диапазона PostgreSQL вызывает HTTP 500

**CONFIRMED/runtime, P2, валидация и контракт ошибок.** Источник: S1 §1.5 — корректная обработка ошибок; S3 — валидация и реальные ответы API.

Код: [main.py:142](../backend/app/main.py#L142) — `positions_count:int=Field(ge=1)`; `VacancySettings` на строке 584; `0001_schema.sql:46` — PostgreSQL INTEGER. Обработаны HTTPException и RequestValidationError, но не эта ошибка записи.

Предусловие: владелец активного проекта с валидными session/CSRF. POST `/startups/{s}/vacancies`: `{"title":"Large","positions_count":2147483648,"application_deadline":"<будущее UTC>"}`.

Ожидание: 422 с Error envelope, если число недопустимо для хранилища. Факт: **500**, тело `Internal Server Error`, не JSON Error. TestClient запущен с raise_server_exceptions=False, поэтому проверен реальный HTTP-ответ, а не только исключение Python.

Последствие: ошибка клиента представляется отказом сервера; фронтенд теряет доменный код ошибки. Транзакция откатывается, потеря старых данных или падение всего сервера не подтверждены. Аналогичное место в PATCH settings установлено по коду, отдельно runtime не исполнялось.

Первопричина: диапазон модели запроса шире INTEGER в БД. Это не основание заменять все ошибки БД на 422.

Минимальное исправление: согласованная верхняя граница создания/settings/OpenAPI (не выше 2147483647 или разумный продуктовый предел). Строгий integer также стоит согласовать с контрактом: Pydantic coercion и JSON Schema — разные политики.

Достаточность: предел, предел+1, очень большое число, PATCH, дробь, строка и bool; невалидные значения дают контролируемый ответ и не меняют БД. Probe: `test_large_capacity_error`.

### F5. Истёкшее рекрутерское приглашение остаётся pending для получателя

**CONFIRMED/runtime, P3, согласованность времени и статуса.** Источник: S2 §5.8, S3 — срок, принятие и reload, S4 — состояние expired в модели/UI.

Код: [main.py:710](../backend/app/main.py#L710), [main.py:721](../backend/app/main.py#L721). Обновление в expired есть при создании приглашений (701) и чтении owner-list (892), но отсутствует в mine и отказанном accept. [App.tsx:1320](../frontend/src/App.tsx#L1320) скрывает действия по клиентскому времени, оставляя сам badge pending.

Шаги: владелец приглашает существующего пользователя; дождаться expires_at; получатель вызывает GET mine и POST accept; снова GET mine. В probe время смещено UPDATE только в временной БД, вместо ожидания.

Факт: accept → **409 INVITATION_NOT_ACTIVE**, но mine по-прежнему `status=pending`. Чтение списка владельцем впоследствии может поменять видимый статус, хотя кандидат уже получил отказ.

Ожидание: пользователь видит expired независимо от действий владельца. Запрет позднего grant уже работает — уязвимость выдачи прав здесь не подтверждена.

Первопричина: несогласованные точки ленивого истечения; исключение в accept откатывает транзакцию, поэтому простого UPDATE перед guard недостаточно.

Минимальное исправление: вычисляемый effective status либо единая процедура истечения с корректным commit-путём. Отделить отказ команды от наступившего временного перехода, как уже сделано для Offer.

Достаточность: только recipient чтение, повторный accept, конкурентные accept/expiry/reinvite; везде один итоговый статус, grant не создаётся, не появляется двойное приглашение. Probe: `test_expired_recruiter_mine_stays_pending`.

## 3. Что не является новой доказанной поломкой

- Старый дефект complete «reset отменяет pending Offer» **исправлен**: resetApplications исключает offer_pending; сервер делает то же. Не повторяю старую находку.
- Учёт мест по названию роли **исправлен**: сервер считает через offers.vacancy_id; макет через member.vacancy ID. Исходный полный набор invariant-проверок проходит, в том числе rename/same title.
- Критическое обновление не портит завершённый joined в исследованных тестах. F1 относится к обратимому withdrawn, а не к старому обвинению «critical меняет все наймы».
- Фальшивый клиентский telegram_id вместо init_data, bool ID, подделанная подпись, дубли полей и автопривязка по имени отвергаются в выполненных тестах.
- Отзыв recruiter grant не отменяет membership или уже выданный Offer автоматически. Изменения под проектной блокировкой проверяют can_manage после ожидания.
- Постороннему запрещены исследованные `/applications/{id}`, attempts/history/solutions, полученные заявки и offers менеджера. Публичность описания проекта/вакансии сама по себе не утечка закрытого письма кандидата.
- В исследованных гонках не получено отрицательной capacity, двойного membership или позднего принятия отозванного Offer.

### Восстановленные автоматы и пересечения

- Startup: active ↔ paused; active/paused → archived. Paused блокирует apply и create_offer; accept старого Offer допускается. Archive атомарно отзывает pending offers/recruiter invitations, архивирует вакансии и закрывает pending/reviewing/offer_pending attempts; активные memberships не удаляет.
- Vacancy: published ↔ intake_closed с ограничением срока/проекта; published/intake_closed → archived. Deadline проверяется отдельно. Условия версионируются независимо от settings (места/дата).
- Attempt: pending → reviewing; pending/reviewing → rejected/withdrawn/offer_pending; withdrawn → pending при restore; offer_pending → joined/declined либо reviewing/closed после revoke/expiry; reset/joined/already_joined → новая current attempt при разрешённой подаче и отсутствии membership. Старый joined при leave не меняется.
- Offer: pending → accepted/declined/revoked/expired. Pending резервирует место; accept переводит резерв в membership в одной транзакции. General offer не расходует vacancy capacity. Pending на другой заявке того же человека/проекта не разрешён.
- Membership: активен до left_at; leave/removal освобождает место, сохраняя offer/attempt. Recruiter invitation/grant — отдельные сущности, не membership.
- Test: новая immutable версия; explicit test_version_id; ordinary сохраняет действительность старой; critical запрещает новые сдачи прошлых версий и supersedes часть незавершённых submissions. F1 показывает неполноту именно этого последнего пересечения.

## 6. Архитектура, данные и API

**Что выдержало проверку.** Monolith/Core + одна SQL-транзакция на запрос — объяснимая архитектура для связанных состояний. Startup row lock — единая точка сериализации мест, offers, membership, версий и grant-изменений. Проверка прав после взятия lock устраняет исследованную гонку revoke/edit. DB constraints связывают application/attempt/offer/member/test по ID, защищают accepted и immutable version-поля. Они не заменяют сервисную сериализацию capacity, о чём SQL прямо предупреждает.

Idempotency receipt берётся под actor/key advisory lock, fingerprint включает method/path/body/If-Match. Повтор результата атомарен с командой. Разные тела с тем же ключом дают конфликт; повтор старого reset после resubmit не сбрасывает новую попытку. Необязательность ключа и сохранение frontend pending-key только до reload уже честно описаны README — это ограничение, а не неизвестная потеря идемпотентности.

**Пределы.** Пагинация материализует всю разрешённую выборку и сортирует UUID до slice. Проверка на 104 записи прошла; объём работы запроса остаётся O(N), all() клиента обходит все страницы. Большая нагрузка на каталог/кабинет не измерялась. Не называю это P1 без подтверждённого ущерба на целевом масштабе; перенос фильтра в SQL — инженерное улучшение.

67 API operations присутствуют в фактических маршрутах и контракте. Штатные tests сверяют routes/refs и representative JSON responses. Это не полное доказательство всех request/response/schema/error комбинаций: F4 показывает выход за Error envelope. Клиентские TS-типы написаны вручную и не содержат всех серверных полей; отсутствие неиспользуемого поля само по себе не ошибка. Для интеграции нужны явные DTO-адаптеры: UUID ↔ demo id, skills array ↔ строка, test_version_id ↔ номер, membership.left_at ↔ active, реальные scopes/permissions/revisions/next_cursor.

Дополнительные **подтверждённые различия слоёв, требующие решения при интеграции**:

- complete разрешает принять recruiter invitation при paused, проверяя лишь «не archived»; backend требует active (`main.py:724`, `complete/main.tsx:1977`). S3 явно гарантирует паузное принятие кандидатского Offer; распространять гарантию на recruiter invitation без решения пользователя нельзя. Это различие, не отдельное выдуманное нарушение требования.
- complete.submitSolution запрещает сдачу при archived vacancy (`rules.ts:277`); backend допускает для оставшейся активной attempt при ещё действующем test deadline (`main.py:829`), потому что архив вакансии сам не закрывает такую попытку. S2 явно запрещает новые отклики/приглашения, но не определяет запрет сдачи старого тестового. Нужна одна согласованная трактовка, не автоматическое ужесточение сервера.
- complete.notifications общие для всех demo actors; серверные recipient_id приватны. Это документированная демо-условность. При интеграции нельзя перенести общий store.notices.
- Новый UI обещает переход из уведомления к событию, но текущий `/notifications` отдаёт только id/title/message/read_at/created_at, без event target. Нужно минимально расширить DTO/route резолвинга либо убрать обещание; переписывание домена для этого не требуется.
- Причина исключения из команды в новом макете и generic DELETE backend не эквивалентны: сейчас сервер фиксирует left_reason='removed', без произвольного текста. Не считать это уже сохранённой серверной причиной.

### История и удаление

API удаления проверяет applications/offers/members/recruiter invitations/grants/test submissions, включая завершённую историю, и лишь затем удаляет owner-generated vacancies/tests/events. Прямая команда не удаляет взаимодействовавший проект. Archive не использует каскадное удаление этих данных. Миграция 0002 валидирует связи/capacity под table locks, отказывается от противоречивого legacy, а не исправляет его удалением. 0003 расширяет users без замены UUID и требует хотя бы одну identity.

Остающийся риск прямых SQL-изменений статусных/ёмкостных данных не объявляется HTTP-уязвимостью: доступ к БД — отдельная доверенная граница. Capacity не обеспечена универсальным SQL CHECK, поэтому будущая новая команда обязана соблюдать startup lock. Это конкретная обязанность поддержки, которую следует объяснить комиссии.

## 7. Telegram и безопасность

Сервер получает raw init_data. Клиентский `initDataUnsafe.user.id` не используется как основание авторизации. `telegram_auth.py` проверяет HMAC-SHA256, дубли query-полей/JSON-ключей, malformed percent/UTF-8, числовой auth_date, будущее время, диапазон и точный int-тип user.id (bool исключён). Выделение секретного ключа через WebAppData и сравнение digest соответствуют проверенному алгоритму S5. Включение полученного signature в HMAC data-check-string не смешано с отдельной схемой Ed25519, где исключаются hash и signature.

Выполненные auth-тесты подтверждают: отказ подделке/другому токену; Unicode и перестановку полей; отказ bool/string/float ID и дублям; offline expiry/future; уникального пользователя при двух разных конкурентных launches одного ID; отсутствие автоматического связывания с demo по имени; сохранение отредактированного профиля; session cookie HttpOnly/SameSite=Lax; CSRF; replay только с уже связанной действующей сессией; новый launch ротирует текущую browser session; logout отзывает её. Это синтетические подписи известным тестовым токеном, не настоящий Telegram launch.

credential_digest канонизирован через рассчитанный HMAC: перестановка полей не создаёт новую credential. Advisory lock сериализует потребление одной credential. Старый initData разрешает только возврат уже связанного live-session профиля, а не новый вход. Replay-строки live sessions сохраняются после пяти минут намеренно, чтобы reload работал семь дней; удаляются после истечения credential и прекращения live session при очередном успешном новом login. В README это описано; формулировка «все записи удаляются строго через 300 секунд» была бы ложной. Сессии/квитанции без периодического GC — эксплуатационное ограничение, а не доказанный захват аккаунта.

Production overlay принудительно выставляет Secure=true, ALLOW_DEMO_LOGIN=false, SEED_DEMO_ACCOUNTS=false и требует секретные env. Caddy-шаблон не доказывает доступность домена. Отключение seed не удаляет старых demo владельцев; миграция их проектов к реальным TG-аккаунтам должна быть явной, что уже оговорено TELEGRAM_SETUP.

**Не доказано**: настоящая WebView-передача initData, поведение cookie Telegram iOS/Android/Desktop, несколько настоящих TG-пользователей, BotFather settings, доступность `test-q-buisness-club.locatermanhass.ru`, HTTPS и сетевой маршрут до частного `192.168.1.10`. Эти действия не выполнялись. Публичный load/rate-limit/DoS аудит не проводился. Наличие/отсутствие защиты периметра нельзя вывести только из Caddyfile.

F3 нельзя называть подделкой Telegram-ID: это другая граница — обязательность завершения профиля уже аутентифицированным пользователем.

## 8. Дизайн, мобильное поведение и доступность

Слои сохранены: final — неизменённая визуальная основа; complete — отдельные формы/правила/localStorage; рабочий frontend — реальный API, новая тема пока только у auth/onboarding. Возврат к старой визуальной основе не предлагается.

После загрузки шрифтов документ и body каждой из 14 страниц имели scrollWidth ровно 320/390 соответственно. Это исходные demo-состояния Ивана, включая пустые списки, не 14 функциональных end-to-end тестов.

Через браузер дополнительно открыт complete cabinet: выбор проекта, список кандидатов, история и actions присутствуют. Исполняемые handlers изучены: native dialog.showModal, возврат фокуса trigger, focus mobile detail, expire перед локальной командой и 30-секундный timer. На исходном final это не новое доказательство серверных прав.

**Ограничения:** в новом проходе не выполнены все формы всех ролей, длинные имена/условия/URL в каждом состоянии, реальная экранная клавиатура, VoiceOver, все browser engines, потеря storage, одновременная запись двух вкладок. Базовый localStorage load/normalize восстановит лишь известные старые поля; потерянные раньше привязки не восстановятся. Прототип прямо помечает unknown member origin и блокирует недостоверный capacity. Это честнее выдуманной привязки.

Native dialog помогает focus/modal behavior, но сам по себе не доказывает всё управление фокусом при ошибках. Рабочий FormDialog и complete dialog — разные реализации. Тест браузерной геометрии не покрывает телеграмные safeAreaInset/contentSafeAreaInset, viewportChanged, BackButton и виртуальную клавиатуру. `frontend/src/telegram.ts` типизирует только initData/ready/expand; необходимых обработчиков платформенного возврата и динамических отступов нет. Это известный незавершённый Mini App слой, не доказанное нарушение исходного обязательного web-прототипа.

Для переноса сохранить новую визуальную систему, заменить локальные мутации API-командами, нормализовать DTO и всегда перечитывать авторитетное серверное состояние; F1/F2/F6 и приведённые расхождения исправить до объявления parity. Не переносить модель localStorage в сервер и не менять backend-модель ради удобства JSX.

Штатный suite действительно выполняет migration upgrade с синтетическими данными, наблюдаемым schema-only legacy snapshot и отказом на противоречиях. Это воспроизведено, а не переписано из старого отчёта. Все возможные исторические схемы v0.1 и production backup/restore не проверены.

## 13. До пяти воспроизводимых демонстраций слабых мест

1. **Withdraw → critical → restore:** выполнить `test_withdrawn_critical_old_submission_revives`, показать reviewed старой версии в активной заявке. Это сильнейший доменный контрпример этого аудита.
2. **«Другое решение» против API:** в макете два решения одной версии сохраняются; на временном API второе даёт TEST_ALREADY_SUBMITTED. Показать одновременно invariant.ts:89–91 и HTTP-ответ.
3. **Первый вход без заполнения:** signed test identity → context true → собственный CSRF → POST startup 201 → context true. Объяснить, что подделка личности не требуется и не выполняется.
4. **2147483648 мест:** одна валидная авторизованная команда создания вакансии даёт 500/plain text. Убедиться, что используется отдельная тестовая БД.
5. **Истёкшее recruiter invitation:** recipient-only GET/accept/GET показывает pending → 409 → pending; затем чтение owner-list меняет статус. Показать зависимость результата от другого пользователя.

Все пять автоматизированы в `test_new.py`; часть демонстрации макета №2 дополнительно выполняет его штатный invariant при build. Не запускать fixture с TEST_DATABASE_URL рабочей базы. Нельзя ради демонстрации публиковать настоящий токен или raw launch credentials.
